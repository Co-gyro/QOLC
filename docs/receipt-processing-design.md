# レセプト処理 設計書 (Phase 1.5)

## 1. 背景・目的

### 1.1 現状の課題
Phase 1 で実装した「提供者が手作業で自己負担額CSVを作成 → QOLCにアップロード」
方式は、以下の問題が判明した:
- 手作業計算によるミスのリスクが高い
- 提供者ごとに独自フォーマットを用意する必要があり、運用負荷が大きい

### 1.2 真の要件
各医療機関・介護事業所は **自社レセコン(レセプトコンピューター)から
ダウンロードしたファイルをそのままQOLCにアップロード**し、QOLC側で
自己負担額を算出して決済する。

業界標準のフォーマット（介護保険給付費請求情報CSV / 医療保険UKE形式）が
存在するため、ほぼ統一仕様で処理可能。

### 1.3 スコープ拡張
| 項目 | Phase 1 | Phase 1.5 (本書) |
|---|---|---|
| 入力ファイル | 提供者独自CSV | 介護保険CSV(国保連統一仕様) + 医療保険UKE(国保連/支払基金) |
| 自己負担額 | アップロードCSVに記載 | レセプトから算出 |
| マッチングキー | 単一の被保険者番号 | 医療保険番号(主) + 介護保険番号(任意) + 過去番号履歴 |
| 対象入居者 | 要介護者中心 | 65歳未満含む全入居者 |

## 2. 対応フォーマット一覧

### 2.1 介護保険CSV（国保連 給付費請求情報インタフェース仕様）
- 文字コード: Shift-JIS (CP932)
- 改行: CRLF
- 構造: コントロール(1) → データレコード(複数2) → エンド(3)
- データ種別:
  - `7111`: 給付費請求情報（事業所単位の集計）
  - `7131`: 居宅サービス介護給付費明細書
  - `7141`: 短期入所生活介護
  - その他複数サービス種別あり
- 自己負担額の取得: 明細書基本情報レコードの「⑪利用者負担額」フィールド（直接記載）

### 2.2 医療保険UKE（電子レセプト形式）
- 国保連向け / 支払基金向け 共通仕様（ただしHOレコード有無で構成差あり）
- ファイル名: `RECEIPTH.UKE` 等
- 形式: 本来は固定長テキスト、サンプルでは xlsx に変換されている
- レコード種別:
  - `HM`: 医療機関情報（先頭1件）
  - `RE`: レセプト共通（患者ごと）
  - `HO`: 主保険（国保のみ、支払基金は無し）
  - `KO`: 公費負担
  - `SY`: 傷病名
  - `SI`/`KA`: 行為（請求項目）
  - `IH`/`HJ`/`JS`/`RJ`/`TZ`: 訪問看護関連の付帯情報
- 自己負担額の取得: **算出が必要**
  - `総請求点数 × 10円 × (1 - 給付率/100) - 公費負担額 - 高額療養費補助`


## 4. マッチングロジック

### 4.1 介護保険CSVのマッチング
```
レセプト明細レコードの被保険者番号で照合:
  1. residents.insurance_number で完全一致 → ヒット
  2. former_insurance_numbers の type="kaigo" 要素で照合
     (サービス提供年月 <= valid_until)
  3. 未マッチ → プレビュー画面に「未マッチ」として表示
```

### 4.2 医療保険UKEのマッチング
```
RE/HOレコードから (保険者番号 + 記号 + 被保険者番号 + 枝番) を抽出:
  1. residents.iryou_* 4項目で完全一致 → ヒット
  2. former_insurance_numbers の type="iryou" 要素で照合
  3. 未マッチ → プレビュー画面に「未マッチ」として表示
```

## 5. 自己負担額算出

### 基本方針（営業ヒアリング 2026-06-04 確定）
**QOLC側で複雑な計算は一切行わず、請求ソフト側で確定した本人負担額を直読する**。

### 5.1 介護保険CSV
明細書基本情報レコードの「**利用者負担額**」フィールドを直読。

### 5.2 医療保険UKE
保険者レコード(HO) の「**一部負担金額**」フィールドを直読。
- 高額療養費限度額処理は請求ソフト側で実施済み
- 公費受給者の自己負担も請求ソフト側で確定
- QOLCは限度額マスタ・所得区分管理を持たない

実サンプル: `HO | 100016 | ま | 717-6128 | 23 | 302580 | 10000`
- 合計金額 302,580円（保険請求総額）
- **一部負担金額 10,000円（本人請求確定額、限度額処理済み）**

### 5.3 特殊ケースの扱い
| ケース | 扱い |
|---|---|
| 生活保護受給者（本人負担0円確定）| 決済対象外（一部負担金額が0または欠落として処理）|
| 54公費等（一部本人負担あり）| 請求ソフト確定額をそのまま決済 |
| 一部負担金額フィールドが欠落 | プレビュー画面で「未確定」表示、決済対象外 |
| 高額療養費限度額超過 | 請求ソフトが処理済の確定額を採用、QOLC独自判定なし |

### 5.4 自己負担割合の判定
レセプトの給付率（70/80/90）から自動判定（A方針採用）。
- 月ごとに負担割合が変わる可能性に対応（後期高齢への変更、所得区分変更等）
- 入居者マスタには負担割合を持たない（管理簡素化）

## 6. UI 変更

### 6.1 入居者登録/編集ダイアログ (resident-form-dialog)
新たなフォーム構成:
```
[必須] 医療保険
  □ 保険者番号    (8桁数字、保険者で異なる)
  □ 記号          (任意、健保組合等で必要)
  □ 被保険者番号  (主キー)
  □ 枝番          (任意、健保組合の被扶養者で必要)

[任意] 介護保険 (要介護認定後に追加)
  □ 保険者番号    (6桁数字)
  □ 被保険者番号  (10桁数字)

[編集モード時] 「保険番号を変更」ボタン
  → クリック時、現番号を former_insurance_numbers に valid_until=今日 で記録
  → 新番号入力欄を表示
```

### 6.2 アップロード画面 (provider/upload)
- ファイル形式自動判定:
  - `.csv` (SJIS) → 介護保険CSVパーサー
  - `.xlsx` または `.uke` → 医療保険UKEパーサー
- プレビュー画面の表示拡張:
  - 「保険負担額」「自己負担額」両方表示
  - 公費受給者の場合は「公費」マーク表示

## 8. ヒアリング結果（2026-06-04 営業 星さん）

| # | 質問 | 回答 |

| 1 | UKE仕様書の入手 | ✅ 厚労省サイトより R08bt1_5_kiroku_nursing.pdf 入手 |

## 9. リスクと懸念事項

| リスク | 影響 | 対策 |
|---|---|---|
| UKE仕様書が入手できない | 自己負担額計算の精度低下 | 業界標準を逆エンジニアリング、ヒアリングで補完 |
| 公費受給者の計算誤り | 過課金事故 | テストパターンを充実、リリース前に対象0件で確認 |
| 月またぎ番号変更の運用ミス | 過去レセプト未マッチ | 履歴UIを直感的に、変更時の警告表示 |
| 高額療養費限度額対応漏れ | 上限超過課金 | スコープ判断後、限度額管理マスタを別途設計 |
