# UD Payment 本実装 開発見積もり（ランサイド実稼働）

作成: 2026-09-16 ／ 対象: モックデモ（/udpay）→ 実決済サービス化

## 前提とスコープ

- **現状**: /udpay は完全モック（1行JSONBストア・決済シミュレーション・認証なしキーゲート）。
  画面・業務フロー（前月コピー→確定→明細メール→アニバーサリー日課金→消込→再決済→領収書）は
  実証済みで、**画面仕様はそのまま本実装の仕様として使う**。
- **本実装のゴール**: ランサイド社員がログインして毎月の請求業務を行い、顧客（歯科医院約22件）の
  登録カードへUSEN会員ID決済で実課金し、明細メール・領収書まで自動化された状態。
- **再利用できる既存資産**（QOLC本番で稼働実績あり）:
  - USEN決済: `lib/payment/member-api.ts`（会員ID決済・HMAC-MD5）／`token-ec-api.ts`＋
    カード登録SDKフロー（`user/card/register`・3DS込み）／取消・返品の運用ノウハウ
  - 基盤: Supabase認証・middlewareロール制御・監査ログ（payment_audit_logs）・
    日次cron（`/api/cron/daily`）・Resendメール送信（support@uni-dev.jp 認証済み）・領収書系
  - デモ実装: 画面一式・計算ロジック（`lib/udpay/logic.ts` はそのまま流用可）・E2E

## 外部依存（開発と並行して解消が必要・開発工数外）

1. **JCB登録型加盟店番号**: 大磯氏への確認→追加申請→発番（会員ID決済とUSEN連携CSVに必須）
2. **USEN連携CSV提出→USEN側登録完了**: ①の番号が揃ってから。テスト決済可能になるまでの期間はUSEN次第
3. **セゾン開通**: DQ欄運用での申請書再提出の要否確認（9/10合意済みの運用）
4. ランサイドからのヒアリング回答（顧客一覧・切替月・メール文面）— 準備一式送付済み

※ 1〜3が長引いても、A・B・D・E・FとUSENテスト環境でのCは先行できる。
本番開通日だけが外部依存でスライドする構造。

## 更新（2026-09-18）

- **CSV一括取込はスコープ入りし、デモに実装済み**（`lib/udpay/csv-import.ts`・SJIS/UTF-8自動判定・
  列名ゆれ吸収・顧客マッチング・テンプレDL）。本実装ではこのライブラリをそのまま流用するため、
  当初の追加見積（+2〜3日）は **+0.5日程度（本実装への配線のみ）** に圧縮。
- デモのシードを月替わり自動更新に変更済み（常設デモの経年劣化対策）。

## スコープ外（今回見積もりに含まない）

- 複数テナント向けのセルフサインアップ・料金請求（UD→ランサイドへの手数料請求は当面手動）
- 白ラベル化（独自ドメイン・ブランド分離）
- セルフィッシュ月次処理（既存ツールで対応可能と確認済み・コード変更不要）

## 主なリスクと手当て

- **本番実課金事故**: 6/29インシデントの教訓どおり、本番ホストガード（ALLOW_USEN_PROD）を
  udpay系APIにも適用。テストはTSJL/TSJMのみで実施し、本番切替は明示手順化
- **USEN登録の遅延**: 外部依存に隔離済み（上記）。開発は止まらない
- **ランサイド側の移行負担**: カード再登録22件。案内テンプレ＋登録リンクで最小化（デモで実証済み）
